# Design

## Context

动机与功能边界见 [proposal.md](proposal.md)。本设计对应 [capture](specs/capture/spec.md)、[desktop-experience](specs/desktop-experience/spec.md) 和 [reminders](specs/reminders/spec.md) 三份增量，当前实现基线为 `main` / `cefa5d5`。

已只读核对当前代码、需求及附近测试：

| 当前事实                                                                                                 | 对设计的约束                                                                                  |
| -------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| `App` 进入 `LifecyclePage`，`LifecycleTaskList` 只有编辑、归档和恢复                                     | 入口接入当前页面，不能以旧 `CapturePage` 的组件测试代替交付                                   |
| 旧 `CaptureService.reparseTask` 和 `ParseQueue` 仍存在，但启动未注册旧 capture 服务                      | 不接回旧启动流程；旧方法缺少调用方 revision，队列使用当前时刻且只在 `editedAt` 存在时保留字段 |
| 当前 `createIntentParser` 已校验请求关联并消费 `create / complete` 联合；服务端时间兜底使用传入上下文    | 复用当前客户端与 `/v1/parse`，重新识别只接受 `create` 分支，不更改服务端路由或完成匹配        |
| `TaskRepository.applyParseResult` 已按 revision 写字段、成功状态并递增版本，但单独调用时结果读取在事务外 | 为 F03 提供包住读取、合并、条件写及返回读取的事务入口；不把读取失败伪装成未提交却留下更新     |
| 数据库版本为 4，只有整条事项的 `editedAt`，无逐字段来源或清空历史                                        | 保留模式按当前空缺统一合并，不推断字段来源，不增加迁移                                        |
| F02 的活动服务可按已提交任务清理或更新展示；现有计划 upsert 会重置触发状态                               | 截止未变化时不调用计划 upsert，避免破坏同次活动及已关闭提醒；成功事实先于计划同步             |
| 主窗口、人物、浮窗各有沙箱 preload，主窗口编辑及 `data:changed` 已独立接线                               | 仅给主窗口增加具体方法，产物保持自包含，不暴露通用 IPC 或解析器                               |

需求取舍已经确定：以 PRD F03 的“保留模式只补空缺字段”为准，统一替代旧队列依赖 `editedAt` 的合并分支。保留模式会保留已有非空原文回退标题；用户要替换标题时明确选覆盖。此前手动清空而现为 `null` 的字段仍为空缺，本次不增加“清空过就永不补充”的历史规则。

## Goals / Non-Goals

**Goals:**

- 让当前完整记录的三态事项都能显式重新识别，保护原始上下文和所有生命周期信息。
- 明确模型调用、版本提交、交付及提醒副作用的不同失败边界，使失败可恢复而不误覆盖。
- 将接口、组件、文件数据库与原生窗口验收串成可追溯证据，保留 F01 / F02 回归。

**Non-Goals:**

- 不将 F03 当成新输入重试，不回退或重开 intake，不修改普通唯一匹配完成语义。
- 不新增识别队列持久化、自动重试、字段历史、撤销栈或模型结果预览步骤。
- 不把任务与提醒计划改造成新的跨模块事务，不承诺计划自动修复；发布和跨平台缺口仍按 Q01 记录。

## Decisions

### 1. 使用独立的已有事项识别服务

新增主进程 `TaskReparseService`，注入任务仓储、当前 `IntentClient`、成功提交联动以及可测试的请求标识生成器。主进程根据事项 ID 读取原文、`recordedAt` 和 `timeZone`，以独立请求 UUID 调用当前解析客户端；不信任 renderer 提供原文、字段、状态或时间上下文。原记录时区非法时在模型调用前拒绝，不以当前设备时区替换。

不接回旧队列：它把重新识别与首次 capture 解析状态写入混合，缺少调用方 revision，并且不能直接接收当前意图联合。F03 不需要排队或重启续跑，用有返回结果的一次受控请求更容易区分失败、冲突和成功。旧独立组件的兼容性通过原测试保留，不做无关删除或批量重构。

### 2. 主窗口专用的请求与结果契约

在 contracts 新增已有事项识别模块，复用 `ReparseMode`、`LifecycleTask` 和适用的已有错误码。建议接口为 `TaskReparseApi.reparseTask({ id, revision, mode })`，请求对象严格限制三个字段，UUID、非负整数版本和模式均校验。

返回判别联合：

- `updated`：完整已提交 `LifecycleTask`，以及 `warning: null | REMINDER_SYNC_FAILED`。
- `failed`：稳定的安全错误码，不带堆栈、SQL、模型正文或密钥。已有网络、配置、非法结果、冲突、存储等错误复用原码；仅为本接口补充 `REPARSE_BUSY`、`REPARSE_UNSUPPORTED_INTENT`、`REPARSE_INTERRUPTED`，不将这些临时错误写进任务或 intake。

主窗口新增 `taskReparse` 窄接口和 `task:reparse` IPC；处理器在服务调用前验证请求，返回前验证结果。preload 仅作类型化调用，运行时契约校验留在主进程及 renderer，避免引入沙箱无法 require 的共享 chunk。人物和浮窗不增加该能力，现有编辑与 F01 接口保持。

采用明确结果联合，便于 UI 区分业务失败、字段已提交但计划同步失败，以及 IPC 结果未送达。后者属于交付结果不确定，提示刷新核对，不假定任务已回退，也不自动再调用模型。

### 3. 确定性合并并作一次事务提交

先验证意图与字段，再在仓储的 F03 专用事务入口重新读取指定任务并核对发起 revision，按以下规则合并，经过 `parsedTaskSchema` 校验后条件写入和读取结果。事务内任一步失败均回滚；不在模型请求期间持有数据库事务。

| 字段                       | 保留模式                                         | 覆盖模式                   |
| -------------------------- | ------------------------------------------------ | -------------------------- |
| `title`                    | 当前合法标题非空，始终保留                       | 采用新合法标题             |
| `contact`                  | 当前非空则保留，`null` 才补充                    | 采用新值，允许 `null`      |
| `dueDate / dueTime` 都为空 | 成组采用新日期与时刻                             | 成组采用新值，允许同时为空 |
| 当前日期非空、时刻非空     | 两者保持                                         | 成组采用新值               |
| 当前日期非空、时刻为空     | 日期保持；仅当结果日期与当前日期一致时补结果时刻 | 成组采用新值               |

不合法的旧截止组合不猜测修复，合并不能通过校验时保留整条旧记录并提示失败。成功只写四个识别字段、`parseStatus = succeeded`、`parseError = null`、`updatedAt` 及 `revision + 1`；`editedAt` 作为已有手动编辑历史标记不重置。即使保留后四个字段未变化，一次成功识别仍可更新上述识别元数据和版本，但不能因此重新安排提醒。

事项 ID、原文、`recordedAt`、`recordDate`、时区、创建时间、状态、完成时刻、完成日期、完成时区和归档时刻均不写入。已完成和已归档事项使用同一字段入口，不经恢复或完成服务。

### 4. 请求占用、冲突和退出保护

主进程按事项 ID 保存会话内 operation token。校验参数及停止状态后，拒绝已有占用；读取并验证调用方 revision，随后在第一次 `await` 前登记 token。不同事项可独立识别，普通编辑和状态操作不被该内存锁阻断。

模型返回后先检查服务仍运行、token 仍匹配，再交由事务入口验证版本并提交。识别期间编辑、圆圈完成、归档、恢复或 F01 的有效任务写入都会递增任务 revision，旧结果因此拒绝；不因用户选择覆盖模式而跳过版本检查。F01 输入处理与 F03 没有共享持久化锁，双方继续遵守任务版本条件，F03 不写其输入状态。

失败不把任务标为 pending、processing 或 failed，也不重写旧 `parseError`；忙碌只保存在本次服务与界面中。`finally` 只释放本 token 的占用。请求结束后可由用户再发起，识别为 `complete` 时返回专用失败，不调用完成匹配、候选或状态方法。

应用清理在数据库关闭前先停止该服务并使 token 失效；停止后的新请求及迟到回调不再读写数据库或广播。复用现有有界 HTTP 超时，不承诺跨退出保持网络请求或持久化占用。普通关闭完整记录只隐藏窗口，已接受请求继续遵守版本条件；显式退出才使未提交操作失效。已经提交后退出则保存成功结果，重启不重放请求。

### 5. 按提交事实联动 F02，分别隔离副作用

事务返回提交前后任务快照后，先调用活动服务的已提交任务核对，再维护计划，最后通知 `data:changed`，各步骤独立隔离失败；不发送 `task:completed` 或 `intake:changed`。

- 对未完成任务，比较提交前后 `(dueDate, dueTime, timeZone)`。变化才调用现有计划同步：未来时刻建立或更新唯一计划，空缺及过去时刻取消待触发计划；F02 立即使旧活动失效，残留旧计划仍由当前任务校验拦截。
- 非截止变化只更新活动标题，保留计划行的状态、触发时间和活动 activationId，不调用会重置计划的 upsert，不重播气泡或延长计时，不恢复已关闭提醒。
- 已完成或已归档任务不能建立计划；可沿用取消待触发计划的清理，活动核对按非 open 状态移除不合法展示。
- 计划写入异常返回 `updated` 加同步警告，不能改成识别失败；任务仍已保存，旧活动先按提交事实失效。广播失败不回滚字段，后续页面查询仍可确认结果。本次不加持久化事件队列或计划修复任务。

与普通字段编辑现有成功接线保持同一行为边界，但不借 F03 改造整个编辑系统。仅在确有复用收益时抽取小的提交后回调，避免接回旧 capture 入口。

### 6. 接入当前页面与可访问确认

`App → LifecyclePage` 注入主窗口新接口，`LifecycleTaskList` 为三态事项增加操作。复用 `ReparseDialog` 的文案和样式并接入 `DialogShell`，默认焦点在保留按钮；覆盖按钮明确说明会替换现有四字段及清空未知可选项。普通打开或取消不调用模型。

请求使用同步 ref 锁防双击，而非仅依赖下一轮 render 的 busy 状态。处理期间禁用本对话框确认和取消，显示可访问忙碌信息；浮窗继续输入、完成事项，版本保护处理由此产生的冲突。

原生检查发现固定提醒面板可能盖住列表最后一行操作。主窗口按提醒面板的实际高度预留末尾滚动空间，随面板及视口变化更新并在卸载释放，使操作可滚到面板上方；不改变浮窗布局、提醒集合或窗口生命周期。最终以原生点击确认入口无遮挡。

对话框保存打开时的任务与 revision，不因数据广播偷偷把旧覆盖选择绑定到新版本。冲突后“刷新记录”通过现有 `listTasks(原事项.recordDate, all)` 读取并定位同 ID；成功后更新确认快照、要求再次显式选择，不再调用模型。读取失败保持错误及重试；事项不存在时说明不可继续，不猜测其他同名任务。

成功的业务结果与页面刷新分别处理：先展示字段已保存及可能的计划警告，再用当前日期的最新刷新函数刷新；刷新失败显示加载重试，不把已提交结果改成识别失败。保留浏览日期、状态筛选、主窗口和浮窗草稿以及 F01 输入反馈。来自旧日期或卸载组件的响应使用请求序号与 effect epoch 失效保护，不能覆盖当前列表、另一个对话框或提示。任务入口移除后恢复焦点到现有合理入口。

## Risks / Trade-offs

- [保留模式不会替换已有非空回退标题，也会补回当前已清空字段] → 在两种模式说明中明确“仅补空缺”，覆盖需显式选择；不声称能还原不存在的字段历史。
- [保留日期与模型时刻可能来自不同日期] → 只有日期相同才补时刻，合并后作整体校验，不静默改动用户保留的日期。
- [识别期间浮窗可能完成或编辑同一任务] → 接受并保留成功任务操作，用旧 revision 拒绝晚到识别，刷新后再次选择，不自动覆盖。
- [字段提交后计划同步或窗口交付失败] → 成功结果与同步警告分开，活动先按已提交任务核对；刷新可观察事实，不承诺新增自动修复。
- [用户在模型等待期间退出或重建界面] → 服务停止 token 和界面 epoch 分别防迟到处理；不存临时忙碌状态，不自动再调用模型。
- [旧队列测试易误当成当前功能通过] → 增加当前页面和真实服务链路验收，并在交付记录明确区分历史证据、模拟及平台实测。

## Migration Plan

1. 先补契约和事务 / 服务，再接主窗口 IPC、preload、当前界面与成功联动；不改正式规格的 Requirements。
2. 保持数据库版本 4，不改写旧任务、intake 或提醒历史；不因升级或启动触发重新识别。
3. 完成 V01—V10 及必要检查后新增 `tasks/verification-f03-task-reparse.md`，按实际结果更新 F03 状态、使用说明及相关已知缺口；未验证平台及后续需求保持原状态。
4. 回退前正常退出。无新增迁移，原有数据库格式保持；成功识别过的字段继续是已保存任务字段，不自动还原旧值。未提交请求随退出失效，旧版仍缺少当前页面的重新识别入口。
5. 规格同步、归档、提交和推送按后续授权执行；本次提案阶段只生成规划文件。
