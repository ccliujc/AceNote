# Design

## Context

动机及功能范围见 [proposal.md](proposal.md)。本设计对应三份增量规格：[capture](specs/capture/spec.md)、[task-lifecycle](specs/task-lifecycle/spec.md)、[desktop-experience](specs/desktop-experience/spec.md)。

已核对的实现约束：

- 当前入口是 `LifecycleService` 与 `App → LifecyclePage`，浮窗也调用同一服务；旧 `CapturePage` 和 `ParseQueue.resume()` 不在启动链路中，不能把旧队列重新接入来代替本需求。
- `IntakeRepository.listRecoverable()` 已查询 `pending / awaiting_selection / failed`，但没有对应页面读取接口。`action`、`selection` 与输入草稿目前主要保存在 renderer 状态中。
- 当前任务识别新增使用 intake UUID，明确转换却生成随机任务 UUID；任务写入与 `markResolved()` 分开执行，`selectCandidate()` 也没有重新验证候选归属。
- 数据库目前是迁移版本 3。intake 没有独立 revision、持久化完成目标或结果任务关联；任务已有 revision 与字段编辑保护。
- 大窗口按需创建、关闭时收起。已有 `focusMain()` 能打开或聚焦完整记录，无需为 F01 增加窗口、托盘或新导航系统。

## Goals / Non-Goals

**Goals:**

- 以本地 intake 为权威来源，恢复当前数据库里的已提交、未处理输入，而不依赖某个 renderer 是否仍存在。
- 让同一输入的并发、重复请求和中断能够得到确定的结果，保护任务及接收上下文。
- 通过有限的契约扩展和增量迁移接入当前入口，沿用已有任务、候选匹配及字段校验逻辑。

**Non-Goals:**

- 不恢复未提交草稿，不自动执行恢复任务，不把整个旧 capture 页面重新启用。
- 不引入持久化任务队列、事件回放系统、分布式锁或多 Electron 主进程共享数据库的新运行模式；输入互斥覆盖同一应用的多个窗口。
- 不修改提醒中心、模型提示词、账号、部署方式或已有事项重新识别。F01 为旧 intake 恢复候选的重新识别不是 F03 的任务重新识别。

## Decisions

### 1. 保留现有状态集合，分开保存状态与显示状态

继续使用 `pending / awaiting_selection / resolved / failed`，不重建带 CHECK 约束的状态列。运行时由单例生命周期服务维护按 intake ID 索引的活跃操作表；恢复视图结合持久化状态与活跃操作提供处理中、处理被中断、识别失败或待确认等用户语言。

- 新建或重试时先取得输入执行权，再以条件更新进入 `pending`；列表读取不能将仍在活跃表中的请求标为中断。
- 启动时在窗口创建前扫描上一会话遗留的 `pending`，在核对已提交结果后标记为 `failed / INPUT_INTERRUPTED`；不调用模型。`awaiting_selection` 保留等待确认，普通失败保留原原因。
- 已提交成功的结果不因 renderer 丢失反馈而回到未处理。只读恢复查询不执行任何业务动作。

选择原因：复用现有状态及查询，避免为 UI 加载状态重做任务状态机。只靠 renderer 的 busy 标志不能覆盖第二窗口，只把所有 pending 都叫失败则会误伤仍在执行的请求。

### 2. 规划版本 4 的增量元数据迁移

拟在 `intake_events` 增加以下字段，并保持原文、接收字段和已有任务不变：

| 字段                | 含义与初始值                                                                             |
| ------------------- | ---------------------------------------------------------------------------------------- |
| `revision`          | 非负整数，旧记录默认 0；状态、完成目标或结果关联有效变更时递增                           |
| `completion_target` | 合法完成意图的目标文字，可空；用于重启后重新计算候选，不保存旧候选列表作为执行依据       |
| `task_id`           | 可空任务外键，指向明确关联的新增、转换或完成结果；未完成的历史创建也可以先建立可验证关联 |
| `resolution_kind`   | 可空的 `created / converted / completed`，记录处理结果类型；旧版不能确定的记录保持空     |
| `legacy_unlinked`   | 旧未处理记录缺少可验证任务关联时为 1，新输入为 0；只用于兼容提示，不通过相同文字猜测关联 |

字段类型、约束与外键通过独立的 `004-input-recovery.sql` 和迁移注册落地；本次只记录方案，不执行 SQL。新增查询按 `received_at DESC, id DESC` 稳定排序，状态索引随查询实测复用或补充，不为每次刷新增加无关持久化数据。

选择原因：仅使用内存无法恢复完成目标和结果；仅依赖相同标题不能证明归属。把整个模型响应或候选列表长期保存也不能保证确认时任务仍然有效，因此只持久化所需目标和明确关联。

### 3. 一条输入的任务结果与终态使用同一事务

在主进程增加基于现有同一 SQLite 连接的事务协调入口，由生命周期服务串联两类仓储；不把 SQL 或事务回调暴露给 renderer。

一次处理的提交顺序为：

1. 在输入级互斥内读取最新 intake，验证未处理状态及调用者看到的 intake revision。
2. 需要模型时，以条件更新记录新的处理 revision，释放 SQLite 事务后等待网络；保存本次操作令牌和关联任务的起始 revision。
3. 响应到达后核对活跃令牌、intake 状态与 revision；已失效的响应不能继续写入，也不能把新的终态改回失败。
4. 在一个短同步事务中重新核对输入及关联任务，创建或更新唯一关联事项，或完成合法候选，同时写入 `task_id / resolution_kind / resolved` 并递增输入 revision。
5. 提交后沿用现有提醒同步和任务事件，再发送输入变化通知；事务回滚时不发成功事件。

网络请求永远不占用数据库事务。识别新增与明确转换统一使用 intake UUID 作为新任务 ID，并写入明确关联；已有确定关联则复用，不能再创建另一条。若关联事项已被手动编辑或完成，应保留其修改并完成必要的输入核对，而不是把晚到字段覆盖进去。

同一输入处理进行中返回 `INPUT_BUSY`；已处理返回 `INPUT_ALREADY_RESOLVED`；过期输入或任务版本使用 `CONCURRENT_EDIT`。这些稳定错误加入共享错误契约，界面据此刷新或保留恢复入口，不能重新 markPending 后再判断终态。

选择原因：确定性 UUID 防止重复创建，事务保证创建、转换或完成不会与输入终态分离；仅加按钮锁、仅检查任务是否存在或在网络等待期间持有事务都不能覆盖这些中断与竞争。

### 4. 恢复候选始终重新计算，恢复操作不沿用自动唯一完成

首次识别得到完成意图时保存 `completion_target`，仍沿用普通输入的唯一匹配直接完成规则。针对已有 `awaiting_selection` 的恢复：

- 使用保存的目标和当前 `open` 任务重新匹配；读取候选本身不调用模型、不修改任务。
- 返回 0、1 或多项均使用恢复专用结果。1 项仍展示确认，0 项展示无匹配及后续操作；不放宽现有普通 `selection_required` 的至少两项契约来改变普通输入语义。
- 确认在同一事务内重新检查输入 revision、完成目标、任务候选归属、状态与任务 revision。不能只校验任务 UUID 存在。
- 旧 `awaiting_selection` 缺少目标时，先返回“需要重新识别以恢复候选”。用户点击该明确操作后，使用原接收上下文识别；该操作仅接受完成意图，随后展示候选，不能自动新增或唯一完成。
- 取消选择只关闭界面；待确认输入与完成目标仍持久保留。任务在候选展示后被其他操作改变时，拒绝旧确认并重新获取候选。

选择原因：保存旧候选 ID 无法证明现在仍匹配；重新请求模型会让离线恢复和稳定性变差。只为确实缺少目标的旧记录提供显式重新识别分支。

### 5. 扩展明确的 IPC 与 preload 契约

新建恢复视图契约，不把 `IntakeRepository` 直接暴露到界面。任务 revision 与 intake revision 分开命名，避免将一个版本误用为另一个。

| 接口或事件                       | 参数与职责                                                                           |
| -------------------------------- | ------------------------------------------------------------------------------------ |
| `recovery:list`                  | 主窗口读取所有未处理输入及显示状态、原因、可用操作、intake revision 和兼容提示       |
| `recovery:summary`               | 浮窗读取待处理总数；不需要拉取全部历史原文                                           |
| `recovery:candidates`            | intake ID、intake revision；返回当前候选、输入版本或需要重新识别的标志，不执行完成   |
| `recovery:reparse-candidates`    | intake ID、intake revision；只在用户请求时为缺少目标的旧输入重新识别完成目标         |
| 现有 `lifecycle:retry / convert` | 增加预期 intake revision；先校验终态和执行权，再处理                                 |
| 现有 `lifecycle:select`          | 保留 `revision` 代表任务版本，增加 `intakeRevision`；确认前重新检查候选归属          |
| `intake:changed`                 | 主进程发送标识、最新输入 revision 及处理状态，不广播原文；主窗口和浮窗收到后重新查询 |

所有 `InputOutcome` 分支携带 intake revision，当前页面失败反馈、浮窗反馈及候选结构同步更新，不能只更新新恢复列表而遗留旧操作绕过保护。`lifecycle:complete` 手动完成接口仍只需要任务 ID 与任务 revision。

主窗口通过独立恢复 API 获取列表与候选，浮窗只增加摘要及输入变化订阅；接口均用共享 Zod schema 校验标识、非负整数版本和结果。人物继续只接收既有任务完成或提醒事件，不增加原文读取入口。

实施验证补充：Electron 沙箱 preload 不加载相对拆分文件或外部工作区包。两个 preload 保持自包含，只运行时依赖 `electron`；主进程用共享 Zod 校验请求、结果和发出事件，preload 再检查事件的最小结构。共有的少量桥接代码保留在各自入口，避免多入口构建生成不可加载的共享 chunk；两个实际入口均纳入覆盖率。

选择原因：专用输入变化事件覆盖“没有任何任务变化但输入失败或开始处理”的情况；复用 `data:changed` 的任务原因枚举不能准确表达它。不给浮窗全量历史列表也能降低重复数据读取。

### 6. 完整记录独立展示，浮窗复用打开完整记录入口

在 `LifecyclePage` 的顶部工作区域增加独立的 `RecoverableInputs` 区域，数量大于 0 时默认展开，内部列表可滚动；它不使用当前每日任务日期或状态参数。条目显示原文、接收日期、原因和可操作按钮，候选复用 `DialogShell` 与候选列表的焦点、Esc、错误保留规则；候选文案需支持只有 1 项的恢复场景。

浮窗在底部入口附近增加轻量的待处理数量与“打开完整记录”操作，沿用 `focusMain()`；不新增全局导航协议，不自动聚焦或创建大窗口。完整记录顶部的待处理入口始终可找到，即使当前正在浏览其他日期。

恢复操作使用自己的状态与反馈，不复用会清空 `draft` 的普通新增成功处理器。恢复失败、成功或另一窗口处理成功都不修改当前草稿、日期或任务筛选。旧 `action / selection` 指向的输入若已处理，应关闭其操作入口并显示已处理提示，而不是播放第二次成功动效。

订阅输入变化后获取快照，刷新使用请求序号保护；事件到达时触发新查询，旧响应不能覆盖新结果。操作后的任务列表与完成统计仍由原数据变化事件刷新。查询失败有单独错误状态，不能把暂不可用渲染成零条。

选择原因：完整记录承担历史恢复，浮窗保持紧凑；直接把所有历史原文放入今日 7 条列表会改变既有产品语义。单独处理恢复反馈可保护用户正在编辑的另一条输入。

### 7. 启动和退出都明确处理活跃操作

数据库迁移完成后，先创建仓储与单例生命周期服务，再执行只涉及 intake 及明确关联核对的启动恢复，最后创建人物窗口。恢复扫描不创建任务、不完成任务、不发送任务完成事件，也不自动请求网络。

显式退出时先使活跃操作令牌失效、停止接收新恢复操作，再走现有调度器停止和数据库关闭；迟到响应不能向已经关闭的数据库写入。尚未提交的 pending 留给下次启动显示为中断，不增加“退出前等待全部网络请求”的阻塞行为。

选择原因：把扫描放在 renderer 挂载后会出现初始数量与状态不一致；等待网络完成再退出会改变现有退出体验。

## Risks / Trade-offs

- [旧版随机 UUID 转换在终态写入前崩溃时，可能已存在没有关联的任务] → 不能只凭文字可靠回填。标识为旧版关联不完整，展示原接收日期和核对已有事项入口，不自动合并、删除或声称已修复过去的重复记录；本变更保证新处理协议及可验证关联的幂等。
- [新旧内部调用签名混用会绕过输入修订保护] → 契约、两个 preload、所有当前失败反馈及候选调用在同次变更中更新，IPC 拒绝缺失版本的恢复写入；旧版整个应用不与新版同时访问迁移后的数据库。
- [任务提交成功后事件尚未发送就退出] → 不回放成功事件，依赖重新查询读取已提交结果，确保不会为补发动画再次执行任务。持久化事件投递不在 F01 范围。
- [提醒同步仍采用既有提交后尽力同步] → F01 保证任务写入与 intake 终态的原子性，不声称提醒计划也已获得崩溃原子性或启动修复；不借本变更扩展 F02。
- [恢复历史数据较多会挤占每日工作区] → 恢复区域内部滚动、浮窗只取数量，不截断数据后伪装为全部；若需分页，保持稳定排序与完整访问能力。
- [用户提交两次相同文字] → 它们仍是不同 intake，不按文本去重；“至多一次”约束针对同一 intake 的操作，不合并用户主动提交的独立事项。
- [原生窗口和网络环境不能由组件测试完整证明] → 通过隔离数据做原生重启和双窗口恢复检查，逐平台记录未验证项，不降低已有测试阈值或用 mock 冒充通过。

## Migration Plan

1. 实施阶段增加版本 4 迁移及共享契约，先在临时数据库验证从版本 1、3 升级及重复启动；本次规划不触碰用户数据库。上线执行前按项目迁移约定准备可恢复的数据副本。
2. 回填 intake revision 与空的目标、结果字段。旧任务 ID 与 intake UUID 完全相同的记录才建立可验证关联；其他旧未处理输入设置 `legacy_unlinked`，旧已处理记录始终保持已处理，不猜测其结果任务。
3. 对明确关联且字段已成功识别、已经手动修改或已有后续状态的任务，只核对并解决输入终态，保留任务现状；对未编辑的旧部分创建保留关联并允许显式重试，不新建另一条任务。
4. 同步更新生命周期服务、IPC、两个 preload 与界面后启用启动恢复。迁移与客户端契约作为一个版本交付，旧未保存目标的候选走明确重新识别分支。
5. 依验证矩阵通过后更新 F01 交付记录及相关旧文档。OpenSpec 主规格的 F01 缺口与 Purpose 描述只在实现验收后更新，需求部分按后续同步或归档工作流合入，不在规划阶段提前改成完成。
6. 回退时先停止新版应用。优先使用前向修复；如必须恢复旧版，应从升级前副本恢复完整数据后再启动，不在用户数据库上做删除列或重建任务表的破坏性降级。升级后新增的数据需在回退前另行保留，不能直接覆盖丢弃。
