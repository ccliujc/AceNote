# Design

## Context

动机及范围见 [proposal.md](proposal.md)。行为要求见 [reminders](specs/reminders/spec.md) 与 [desktop-experience](specs/desktop-experience/spec.md)。下列发现来自当前入口及对应测试，不以历史已勾选任务替代入口可用性：

- `main/index.ts` 在调度成功后直接广播 `reminder:due`，没有当前会话活动集合；`LifecyclePage` 只在收到事件后向本地数组追加提醒，没有初始化查询。
- `registerReminderIpc()` 的关闭处理只检查 UUID；页面请求返回后自行过滤卡片，主进程及人物不知道关闭结果。
- `ReminderRepository.listActive()` 查询所有 `fired`，没有会话、关闭或任务状态边界，不能直接接到新查询接口。
- `upsertForTask()` 按 `task_id` 更新且复用原提醒 ID，已有测试明确断言 ID 不变。单靠这个 ID 关闭可能误伤改期后的下一次提醒。
- `ReminderService.syncTask()` 只取消 `scheduled`；对已触发提醒的展示没有联动。`LifecycleService` 在任务提交后尽力同步提醒，异常不撤销任务；编辑回调目前还有把提交后同步异常透传为编辑失败的路径。
- `PetApp` 只保存消息文字与两个独立定时器，没有来源身份，当前无法精确判断哪个提醒被关闭。
- F01 已使用版本化状态、快照失效处理及自包含沙箱 preload。F02 可沿用这些原则，但活动提醒的集合、会话及触发身份独立于 intake revision。

主要依据：[调度器](../../../../apps/desktop/src/main/reminder-scheduler.ts)、[仓储](../../../../apps/desktop/src/main/reminder-repository.ts)、[提醒服务](../../../../apps/desktop/src/main/reminder-service.ts)、[IPC](../../../../apps/desktop/src/main/ipc.ts)、[完整记录](../../../../apps/desktop/src/renderer/lifecycle-page.tsx)、[人物](../../../../apps/desktop/src/renderer/pet/pet-app.tsx)、[提醒回归](../../../../apps/desktop/test/reminder-lifecycle.test.ts)。

## Goals / Non-Goals

**Goals:**

- 为同一应用主进程中的所有窗口提供同一份本会话活动提醒，晚打开的窗口能读取，旧请求不能恢复已关闭内容。
- 明确计划记录、实际触发、活动展示与人物气泡四者身份，可靠处理重复关闭、改期和消息替换。
- 让活动失效核对独立于可能失败的计划写入，保持已提交任务结果与界面一致。

**Non-Goals:**

- 不增加数据库迁移、持久化关闭历史、跨会话活动恢复或多个 Electron 主进程共享活动集合。
- 不扩展提醒计划种类，不引入系统通知、持久化事件发件箱、后台唤醒或任务与提醒计划的全面事务改造。
- 不把旧 `CapturePage` 接回主入口，不把 F03、安装包、配置界面或整个 Q01 发布验收纳入本变更。

## Decisions

### 1. 当前会话状态由主进程独占，数据库继续保存计划与触发结果

拟增加独立的 `ActiveReminderService`，与现有负责计划计算的 `ReminderService` 分工；两者由应用入口持有。启动时创建 `{ sessionId, sessionStartedAt }`，供活动状态和调度器共享。活动集合初始为空，不通过 `listActive()` 恢复历史 `fired`。

活动状态包含本会话唯一标识、单调递增 `revision` 和活动条目；按 `scheduledAt`、稳定标识排序，条目不得因每日日期、状态筛选或浮窗 7 条限制被截断。只有实际成功抢占的到期计划可以新增活动条目，登记所需数据先校验，抢占成功到登记之间不插入异步等待或外部回调。先登记再交付窗口事件；交付失败不能撤销已登记状态，也不能阻断其他提醒。

关闭仅改变内存活动集合，不把计划伪装为任务完成，不额外写 `dismissed` 数据库状态。退出清空会话；原 `scheduled / fired / cancelled / missed` 语义及启动错过扫描保留。数据库仍为 F01 迁移版本 4。

备选：为 `fired` 增加持久化关闭列或直接向页面返回历史 `listActive()`。前者引入本需求不需要的迁移与跨会话含义，后者会混入旧会话及已失效提醒；均不采用。

### 2. 每次实际触发使用独立 activationId，不修改既有计划 ID 约定

成功抢占生成一次 `activationId`，由主进程在内部触发链路携带；同一次登记和交付复用该值。活动条目保存 `{ activationId, reminder }`，其中 `reminder` 沿用已有显示字段。内部另保存触发时的计划引用及截止签名，包含计划 ID、任务 ID、计划时刻、截止日期、具体时刻和时区，用于核对当前任务与计划。

对同一实际触发的重复登记使用该标识去重，包括关闭后收到的重复登记；本会话已见标识只保留身份信息，退出释放，不提供历史查询。重新排期再触发取得新 `activationId`，即使数据库 ID 相同也不是旧卡片。卡片与气泡的展示身份均使用会话及触发引用，不按标题判断。

关闭请求只需要 `{ sessionId, activationId }`，不要求整个集合的 revision 相等，避免无关提醒到达时错误阻止本条关闭。主进程在一次同步操作内检查会话并移除精确条目：

- 当前会话、条目仍活动：移除，版本递增，广播并返回最新快照。
- 当前会话、引用已经不活动：幂等返回最新快照，不影响同任务的新条目。
- 会话不符：报告 `CONCURRENT_EDIT` 并要求刷新；非法或缺失标识在入口拒绝，无副作用。
- 关闭已提交但结果交付丢失：重试和查询仍看到已关闭，不恢复旧卡片。

不保留只传数据库 ID 的关闭绕过入口。备选的“关闭任务的当前提醒”或“计划 ID + 页面数组过滤”都不能准确保护新的触发。

### 3. 全量快照与版本化事件衔接，查询不触发气泡

拟新增以下共享契约；最终名称可依代码风格微调，身份与版本语义不得改变：

| 契约                      | 字段与用途                                                                                    |
| ------------------------- | --------------------------------------------------------------------------------------------- |
| `ActiveReminder`          | `activationId` 与既有 `ReminderView`                                                          |
| `ActiveReminderState`     | `sessionId`、非负整数 `revision`、有序 `reminders`；显式允许空数组                            |
| `DismissActiveReminder`   | 严格的 `sessionId`、`activationId` 两字段请求                                                 |
| `reminder:active-changed` | 完整的 `ActiveReminderState`，用于幂等替换显示状态                                            |
| `reminder:due`            | 保留 `reminder`，增加 `sessionId`、`activationId` 及本次登记后的 `revision`；仅用于新到期反馈 |

完整状态事件让客户端无需补齐增量缺口；关闭返回相同状态契约。新增、移除及可见内容更新才递增版本，重复关闭不递增。广播回调失败被隔离，已有权威状态保留，下一次查询可修复界面。快照生成前完成有效性核对，不把核对读取失败当成空集合；批量核对先得到完整结果再应用，避免把半份读取结果伪装成完整快照。

客户端先订阅再请求快照，接收首份有效权威状态时绑定会话；之后只应用同会话且版本更新的状态，相同版本不重复触发效果，丢弃较旧状态。首个查询晚于事件返回也不会覆盖新状态。组件卸载使待返回请求失效并取消订阅；手动重试复用同样规则，不重新挂重复监听。版本属于活动集合，不与 F01 输入版本或任务修订混用。

备选的“先查再订阅”存在事件缺口；“每次变化仅广播无版本的刷新提示”无法可靠区分旧查询，因此不采用。

### 4. 活动有效性独立核对，覆盖所有当前任务提交入口

成功任务写入后，把已提交任务数据交给活动服务核对，再独立执行原计划同步。覆盖字段编辑、自然语言及圆圈完成、候选确认、F01 恢复完成、归档、恢复、新建及转换等当前入口，不依赖某个页面是否已打开。

| 已提交变化                           | 活动展示                                       | 计划行为                       |
| ------------------------------------ | ---------------------------------------------- | ------------------------------ |
| 完成或归档                           | 移除所属活动条目                               | 取消仍待触发计划               |
| 移除截止信息，或改变日期、时刻、时区 | 移除原触发，不把未来计划直接加入活动集合       | 沿用原规则安排未来，过去不补发 |
| 恢复为未完成                         | 不恢复旧活动展示                               | 只在截止仍未来时重新安排       |
| 只改标题、对接人等非截止字段         | 保留同一触发，标题变化更新卡片与仍可见气泡内容 | 不重播旧提醒或重置气泡计时     |
| 任务写入失败                         | 保留原有效条目                                 | 不基于失败请求更改活动状态     |

不能把活动失效清理放在可能抛错的计划写入之后。沿用任务已提交就不因提醒同步失败撤销结果的规则，并修正编辑回调把提交后同步失败冒充任务写入失败的路径；数据变更通知仍须送出。此处只统一 F02 的提交后接线，不增加任务与计划的新事务。

快照和关闭前还要根据最新任务、计划核对；正常轮询中也执行核对，修复遗漏的展示失效。核对检查任务是否 `open`、截止签名及对应计划触发是否仍有效，而不是仅比较任务 revision：普通改名也会增加任务 revision，但不应移除提醒。对仍有效的改名更新显示快照，不再次发 `due`。

待触发计划也必须在抢占前重查当前任务，并用既有 `reminderAt` 验证当前截止信息计算出的计划时刻与候选一致。计划写入失败留下的旧 scheduled 不能在改期后重新进入活动集合；仓储候选读取需允许在形成合法视图前排除已无截止信息的旧行，单条失效记录不得阻断其他有效计划。核对和成功抢占之间不插入异步等待；此处只阻止错误触发，不新增计划修复队列。时区签名指已有任务保存字段，不新增时区编辑入口，也不因设备时区改变重写任务。

存储读取不可用时返回可理解的查询错误，保留最后已知状态，不猜测关闭成功；后续查询或轮询可恢复。提醒计划同步失败本身不意味着 F02 负责重建所有丢失计划，也不增加跨重启修复队列。

### 5. IPC 与 preload 按窗口保留最小能力

| 使用方                     | 拟暴露能力                                                                                   |
| -------------------------- | -------------------------------------------------------------------------------------------- |
| 完整记录 `window.reminder` | `getActiveReminders()`、`onActiveRemindersChanged()`、`dismissReminder(reference)`           |
| 人物 `window.pet`          | 上述活动状态的只读查询与订阅、带触发引用的 `onReminderDue()`；保留已有任务完成与人物操作接口 |
| 日程浮窗                   | 沿用现有 API，不增加提醒读取或全局关闭接口；手动完成通过统一任务链路使活动提醒失效           |

`registerReminderIpc` 接收活动服务，不再是空处理器。主进程用共享 Zod schema 校验请求、返回快照和事件；preload 验证必要事件结构并返回可取消的订阅。两个受影响的沙箱 preload 自包含，不引入运行时工作区包或相对共享 chunk，保持 `contextIsolation`、`sandbox` 与 Node 集成设置。

同步更新 `ReminderApi`、`PetApi`、`ReminderDueEvent` 和体验事件联合 schema，以及当前调用与测试桩。没有不带触发引用的兼容关闭方式；旧整包应用不得与新版模块混合使用。此调整不涉及公开解析 HTTP 接口。

### 6. 提醒中心只消费权威状态，人物仅对匹配来源收起

完整记录使用独立活动状态 hook，区分初次加载、真实空态、查询失败及保留旧快照的刷新失败；失败可重试，卡片区域可滚动且不劫持输入焦点。卡片 key 使用 `activationId`，按条目锁定关闭按钮，等待权威状态后移除。操作异常时重新获取状态；若主进程实际已关闭，不把结果丢失当成理由重新插入旧卡片。

`PetApp` 为当前气泡记录来源：完成消息与提醒消息分开，提醒消息附会话及触发引用。视觉叉号及 15 秒计时只调用本地收起；全局快照表明当前提醒已消失时，只取消匹配来源的消息计时并收起，不清理后来的完成动效或其他消息。旧定时器继续遵守消息令牌保护。

人物先衔接活动快照和订阅，新的 `due` 反馈仅在对应引用仍有效时显示；初始化未完成的到期提示暂存并核对，已失效、重复或旧引用不重新弹出。查询、组件重新加载及纯标题更新不生成新到期反馈；更新仍可见同次提醒的文字时不重置其剩余计时。多条同时到期继续按现有单气泡替换方式显示，完整记录保留全部活动项，不新增人物消息队列。

### 7. 启动和退出保持单次清理与浮窗优先

应用入口先建立活动服务、共享会话和 IPC，再创建人物并启动调度；快照或提醒到达不能调用打开完整记录。完整记录关闭时仍只隐藏，活动状态留在主进程；页面重建后查询当前集合。

显式退出先使业务操作失效并停止调度，再停止活动服务和发出事件的能力，最后关闭数据库；重复清理安全。排队的旧定时回调不能在停止后访问已关闭连接或再次登记提醒。退出不等待网络，不持久化活动或关闭状态。

## Risks / Trade-offs

- [改期复用数据库提醒 ID] → 使用独立会话与触发引用，并在服务和界面均验证身份，测试旧关闭不能误关新提醒。
- [快照与事件先后交错] → 先订阅、版本化全量状态、丢弃旧响应；关闭结果也走相同状态合并。
- [任务成功而提醒计划同步失败] → 活动核对使用已提交任务并独立执行；查询与轮询再次核对，不让异常伪造回滚或空列表。
- [数据库 claim 与内存登记之间进程退出] → 本需求不承诺崩溃后恢复活动提醒；新会话为空，不能为了补这个间隙自动重放历史触发。
- [主进程状态改变后事件丢失] → 查询可恢复；已停止或销毁的窗口不影响主状态，广播异常不回滚关闭。
- [会话内全量广播与去重标识占用] → 仅携带活动显示字段和身份；去重集合只保存标识并在退出释放，不建立历史中心。
- [旧测试只断言当前页面移除] → 新增真实服务到两个 renderer 的集成断言，并保留原提醒时间、F01 恢复、圆圈完成及窗口生命周期回归。

## Migration Plan

1. 先扩展共享契约及纯状态测试，再实现主进程活动服务和调度、任务提交接线；不改表结构或旧行的身份约定。
2. 在同次交付中升级提醒 IPC、主窗口和人物 preload、当前 renderer 与测试桩；不允许旧关闭签名静默绕过身份检查。
3. 通过下方 V01—V10 与必要原生验收后，更新 README、F02 交付记录及相关文档的实际状态。正式规格的 Requirements 在后续同步或归档时合入，本次规划不更改基线完成状态。
4. 回退时正常退出并恢复整包版本，不降级 F01 数据库；活动内存随退出消失，原任务和已有计划继续保存。旧版仍有原先的提醒展示局限，回退说明如实记录。
